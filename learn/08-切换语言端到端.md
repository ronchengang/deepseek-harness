# 端到端纵切:把语言从 English 切到 日本語,发生了什么

> 把「切语言」从点击一路跟到存储,串起前端插件、Cordis 服务、后端 settings 服务、落盘文件。
> 来源(都在代码里坐实了):`packages/client/locale/src/client/index.ts`、`LanguageRow.tsx`、`locale-settings.ts`、`packages/client/locale/README.md`、`packages/settings/settings`、`packages/boot/config-editor`。

## 一句话答案

- **怎么生效**:`setLocale('ja')` 立刻更新前端内存里的 `LocaleRuntime` 快照并推一个新 revision,所有用 `t` / slot 渲染的 UI **当场重渲染**(无需刷新),同时把 `<html lang>` 改成 `ja`。
- **存在哪**:异步写给后端 settings 服务,最终持久化到 **`$DSH_HOME/cordis.patch.yml`** 里的 `locale.preference: ja` 字段(默认 `~/.dsh/cordis.patch.yml`)。
- **本质**:它存的不是「一个应用设置」,而是 **Cordis 的一条 profile patch**——即改的是「locale 这个插件的运行时配置」,靠 Cordis 的 volatile config 机制不 remount 就更新。

## 完整链路(9 步)

```
① 用户在「语言」行菜单选「日本語」
   LanguageRow.tsx 的 Menu onSelect(id='ja') 回调
        │ 调用注入进来的 setLocale(id)
        ▼
② LocaleRuntime.setLocale('ja')   —— 唯一的偏好写入口
   (packages/client/locale/src/client/index.ts)
        ├─ a. this.preference = 'ja'
        ├─ b. 若 active 变了 → this.publish('ja', localeChanged=true)   ← 前端立即生效
        └─ c. void this.host?.set('preference', 'ja')                   ← 异步持久化
        ▼
③ publish():冻结一个新快照 { active:'ja', locales, revision+1 }
        ├─ emit('locale/change', snapshot)
        └─ 通知所有 LocaleFace 订阅者(listeners)
        ▼
④ UI 当场重渲染(两条刷新通道):
        ├─ 框架注入的 t 座位背后就是这个 LocaleFace 的 getSnapshot/subscribe
        │   → 每个用 t(...) 的 slot 组件 re-render,显示日文
        ├─ sync() 把新 active/options/revision 推给「语言」行自己的 store
        └─ syncDocumentLanguage() 把 <html lang> 改为 'ja'
        ▼
⑤ host.set('preference','ja')  —— host 是 ctx.configForms.get('locale')
   (ui-settings 的 ConfigForm,命名空间 'locale')
        │ 走 remote(settings 命名空间)发给 Host
        ▼
⑥ 后端 settings 服务收到:校验 locale 的 Config schema
   字段定义在 locale-settings.ts:preference 是 z.string().pattern(BCP47).required(false)
        │ 校验通过
        ▼
⑦ config-editor 把它写进 active profile 的 patch
   (packages/boot/config-editor)
        ├─ 先 reconcile 外部改动,锁 profile manifest
        ├─ 原子替换 locale 条目的 config override
        └─ 保留 YAML 注释和 !!js 表达式,只替换目标值
        ▼
⑧ 落盘:$DSH_HOME/cordis.patch.yml
   出现/更新一行类似:
        locale:
          preference: ja
        ▼
⑨ Loader 应用这条 patch(volatile config)
   locale 插件的 Node 半声明 preference 是 Volatile<string>
   → 不 remount 插件就把新值投影给浏览器
```

## 关键设计点

### 1. 「生效」和「存盘」是解耦的两件事

`setLocale` 里 b 和 c 是分开的:
- **b(生效)** 是纯前端、同步、立即的——改内存快照 + 通知订阅者。所以 UI 瞬间变日文,不等网络。
- **c(存盘)** 是 `void this.host?.set(...)`,异步发给后端,**不 await**。即使存盘慢或失败,界面已经先切好了。

这就是 README 说的「User selections take effect immediately」。

### 2. 为什么「选当前已经是的语言」也会写盘

代码注释特意解释了:active 值可能只是**临时值(provisional)**——比如新浏览器根据 `navigator.languages` 猜的,或 fallback 到的英文,**还没人存过**。用户明确点一下,哪怕和屏幕上一样,也是一次显式选择,必须落盘,这样**同一个 DSH home 下的另一个浏览器**也能读到。所以 `host.set` 无条件执行,只有「要不要通知重渲染」是有条件的。

### 3. 存的是 Cordis 配置,不是独立的「设置数据库」

这是最能体现「一切皆插件」的地方:

- locale 偏好没有专门的存储表,它就是 **locale 这个插件的一个配置字段**。
- 存储介质是 Cordis 的 **profile patch 文件 `cordis.patch.yml`**——和你手写 `--patch` 覆盖插件配置用的是同一套机制。
- 应用方式是 Cordis 的 **volatile config**:插件 Node 半把 `preference` 声明成 `Volatile<string | undefined>`,Loader 更新这个字段时不需要卸载重挂插件。

换句话说,「改设置」= 「改这个插件的配置行」=「往 profile patch 写一条 override」。后端的 settings 服务(`packages/settings`)就是「把 Config schema 投影成可编辑表单 + 把编辑存进 active profile patch 让 Loader 应用」。

### 4. 存储作用域:每个认证浏览器共享同一份

README 的 Known Limitations 明确:**同一个设置文档被所有认证浏览器共享**,不是 per-browser。因为它存在 `$DSH_HOME` 下,共享这个 home 的客户端(Web、Desktop)读的是同一份 `locale.preference`。

### 5. 新浏览器的「临时语言」从哪来

在 Host 存的偏好读回来之前,前端先用一个**临时值**顶着:
- `navigator.languages` 按「完整 tag → 主子标签」匹配已注册语言,都不中就 fallback 到英文。
- Host 的偏好读取在插件激活**之后**才跑(这样设置服务不可用也不会卡住页面),读到后**实时替换**临时值。
- 桌面壳还能通过 `__DSH_LOCALE__` 桥提供系统语言和 Host 偏好,但**只有 Settings 里的显式选择才会写 `locale.preference`**,自动检测始终是临时的。

## 一个可验证的小实验

切一次语言后,去看 `~/.dsh/cordis.patch.yml`(Windows 是 `%USERPROFILE%\.dsh\cordis.patch.yml`),应该能看到 `locale` 条目下多出 `preference: ja`。把这行删掉或改掉,重开页面语言就跟着变——因为它就是一条普通的 Cordis 配置 patch。
