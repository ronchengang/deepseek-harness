# 怎么理解「前端界面也是插件」

> 来源：`packages/client/README.md`、`packages/client/AGENTS.md`、`docs/subsystems/web-client.md`、`docs/subsystems/slots.md`、`docs/subsystems/client-modules.md`。

## 一句话

**前端和后端用的是同一套 Cordis 框架。** 浏览器里也跑着一个 Cordis context，一堆 `@deepseek-ai/dsh-client-*` 插件往这个 context 注册「服务」和「UI 片段」。界面不是一个写死的 React 应用，而是由几十个 UI 插件在运行时**组装**出来的。

看一眼 `packages/client/` 下的目录就懂了：`ui-conversation`、`ui-chat`、`ui-sidebar`、`ui-settings`、`ui-approval`、`ui-tool`、`ui-plugin-manager`…… 每一个都是一个独立的插件包，对应界面上的一块区域或一个功能。

## 后端插件 vs 前端插件：同构但不同「货币」

| | 后端（Host）插件 | 前端（Client）插件 |
|---|---|---|
| 框架 | Cordis | **同样是 Cordis**（浏览器里也有 context） |
| 贡献什么 | service、typed event、工具 schema | service、**UI Slot**、React 组件 |
| 注册方式 | `ctx.tools.register` / `ctx.on` / `ctx.effect` | `ctx.slots.register` / `ctx.slots.registerFactory` |
| 包名 | `@deepseek-ai/dsh-<name>` | `@deepseek-ai/dsh-client-<name>` |
| 组合来源 | profile 的 bundle | 同样经 bundle（`bundle/web-app`）声明 |

所以你原来的理解要修正一点：**不是「后端是插件、前端是普通界面」，而是前后端都是 Cordis 插件树，只是前端插件贡献的是「界面片段」而不是「后端能力」。**

## 前端插件怎么拼出界面：Slot（槽）系统

这是前端插件化的核心机制，相当于后端的「事件/服务」在 UI 层的对应物。

### 基本模型

- **Slot（槽）= 一个父组件开放的扩展位置**。谁拥有这个位置，谁就 `ctx.slots.register({ name, children?, store?, inject? }, Component)` 声明它。
- 只有外壳（shell）能渲染根 slot `'root'`，其余 slot 层层嵌套。
- Slot 名字镜像组合路径：`<domain>.<entry>.<hole>`，比如 `'tool.call.toolview'`（工具调用卡片里放每个工具视图的那个洞）。
- 一个组件能渲染的 slot，**恰好**是它注册时 `children` 里声明的那些 key。渲染没声明的 slot，或重复声明别人已声明的 slot，**在加载时就报错**。

### 往别人的槽里塞东西

一个功能插件想在别的插件开的槽里加东西，用：

```ts
ctx.slots.inject(name, () => ctx.slots.register(...))
```

它会等那个 slot 真正被声明后再注册；声明消失时自动移除；重新声明后重跑。这跟后端「注册是可撤销副作用」是一个思路。

### 结果

界面 = 一棵 Slot 树，从 `'root'` 往下，每个节点由某个插件提供的组件填充，节点内部又开放更多 slot 给其他插件填。**加一个 UI 功能 = 写一个插件，往某个 slot 注册一个组件**，不用改主程序。

## 数据怎么流到组件（为什么组件里看不到 ctx）

这是前端插件化很严格的一条红线：

> **组件（所有 `.tsx`）永远看不到 `ctx`。** `ctx` 只属于 `apply` 世界（插件主体和它的 inject 工厂）。

组件只通过「五类 props 份额（the five shares）」拿数据和回调：

1. `PropsRuntime` — owner 数据 + scope/global 座位
2. `PropsRenderSlots` — children（能渲染的子 slot）
3. `PropsRenderFactories` — `renderFactorySlot`
4. `PropsStore` — store
5. inject 面 — 从 apply 闭包的 ctx 取出的**纯数据和回调**

活数据只有三条通道：父组件知道 → owner props；只有组件自己知道 → 本地 state；跨 entry 共享或要活过重挂载 → 一个在 register 时声明的 store。

框架 hook（`useSession`、`useSessions`、`useStore`、`renderSlot` 等）只能由框架生成，业务代码不能自己造 hook 当 prop 传。

这套纪律的目的：**让「表现层组件」成为纯粹、可整体重写的消费品**，所有跟 ctx / 服务 / 传输相关的东西都挡在 apply 层和渲染机器层之外。

## 三层单向知识（前端内部架构）

`packages/client/AGENTS.md` 定义了前端栈的单向知识分层：

1. **数据对象层（React-free）**：`client/connection` 管传输，`session-controller/client` 管 `ClientSessions → SessionManager → Session`，`client/store` 管快照存储引擎。产物是「裸可观察源」，没有 hook 成员。
2. **渲染机器层（`ui-renderer`，一个动态插件）**：所有 ctx-到-React 的集成都在这——slot 渲染器、`SessionProvider`、useSyncExternalStore 适配器。每个 hook 都在这里从裸源组合出来。
3. **表现组件层（各插件包的 `src/client/`，纯 props）**：预期会被整体重写，业务逻辑不许泄漏进来。

红线：**业务数据活在对象层，不在 store**。store 只放共享的「查看/交互状态」（选中项、草稿、面板宽度）；会话、帧、连接留在对象层。而且**「怎么画」的东西绝不进 session 日志**——工具卡片是在前端从原始 call/result 事件 + 持久化的结果元数据推导出来的。

## 前端插件也有「模块图 + DI」两层

前端比后端多一个复杂度：浏览器要动态加载 JS bundle，所以有两种「依赖」声明，不能混：

| | Cordis 服务 `inject` | 模块图 `external` |
|---|---|---|
| 单位 | 服务名 | 模块说明符（module specifier） |
| 时机 | 运行时，fiber 会等 | 物化时，`require` 是同步的，不能等 |
| 没满足 | 一直 PENDING，无超时 | 当场抛错 |
| 谁能满足 | 任何提供该服务的插件，可替换 | 唯一的那个模块身份，不可替换 |
| 环 | 允许 | 拒绝 |

简单说：**Cordis DI 管「服务依赖」（可等、可替换），模块图管「代码能不能被同步 require 到」（不可等、不可替换）**，模块图在 Cordis DI 之下。一个前端插件要被 Cordis 激活，它的代码必须先能被模块系统物化。

## 落到 Desktop

回到上一篇笔记的问题：Desktop 的「前端」就是这棵 Cordis 前端插件树（跑在 Electron 窗口的 Web 文档里），「后端」是 Host 子进程那棵后端 Cordis 插件树。两棵树通过 RPC/WebSocket 连接，而 Desktop 和纯 Web 跑的是**同一棵前端树**，只是 Desktop 额外塞了几个 Desktop 专用的 client 插件（比如 `ui-directory-picker-native`、`ui-sidebar-browser` 的桌面适配）。

## 新增一个前端功能大概要做什么

（摘自 `packages/client/AGENTS.md` 的 new-plugin checklist，帮助建立体感）

1. 建包骨架 `packages/client/ui-<name>`，`package.json` 带 `dsh.client` manifest，导出 `./client`。
2. 三个注册面缺一不可：`tsconfig.client.json` 聚合里加 references；`bundle/web-app/cordis.patch.yml` 加一行 `dsh.client`；`bundle/web-app/package.json` 加依赖。
3. 在 `apply` 里用 `slots.register` 或 `slots.inject(...).register(...)` 把组件挂到某个 slot。
4. 组件只吃五类 props，不碰 ctx。
5. 样式只用 CSS token，文案进本地化字典，注释用英文。
