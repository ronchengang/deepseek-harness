# 案例拆解：设置页是一个插件还是多个插件？

> 来源：`packages/client/ui-settings/README.md`、`ui-settings-general/README.md`，以及 `packages/client/` 下的 `ui-settings-*` 系列包。

## 直接答案：多个插件

那张设置页**不是**一个插件,而是「**1 个 seam 基座 + 1 个外壳 + 若干内容/功能插件**」协作拼出来的。这正是上一篇「前端也是插件」最好的实例。

## 三种角色

### 1. 基座(seam / 服务,不画界面)——`ui-settings`

- 包:`@deepseek-ai/dsh-client-ui-settings`
- 它**自己不渲染任何界面**。它提供的是:
  - 配置表服务(`ctx.configForms`):命名空间隔离的读写、原子多字段更新、schema 校验、防并发覆盖。
  - 浏览器里唯一的 `settings.describe` 读取器(一份共享的设置文档镜像)。
  - **声明那些 slot 类型**:`settings.section`、`settings.general.item`、`settings.plugins.tab`、`settings.onboarding`、`settings.launcher` 等。
- 换句话说,它是「设置」这个能力的 Service Definition——定义了大家往哪儿塞东西、怎么存。

### 2. 外壳(画出面板框架)——`ui-settings-general`

- 包:`@deepseek-ai/dsh-client-ui-settings-general`
- 它渲染你截图里看到的**外框**:
  - 左侧导航列表(「通用设置 / 模型 / 内置插件 / Agent 预设」这几个条目,是 `settings.section` 账本的投影)
  - 标题「设置」、右上角「打开配置文件」按钮、关闭 ×
  - 侧边栏底部那个打开设置的触发器、断线重连指示、服务版本变更对话框
  - **「通用设置」这一个 section 的内容容器**
- 注意:它只自带两行——「Coding Tools 开关(显示代码工作视图)」和「当前版本」。**其余每一行都是别的插件注册进来的。**

### 3. 内容/功能插件(往槽里塞具体条目和页面)

左侧每个导航项、右侧每一行,基本都来自独立的插件:

下面这张表是在代码里 `grep` 注册点坐实的(不是推断),括号里是注册时的 `id` 和 `order`,order 决定上下排序:

## 一个容易忽略的细节:谁声明槽 vs 谁渲染槽

搜代码发现一个很能体现「职责分离」的设计(见 `ui-settings/src/client/contract/slots.ts` 的注释):

- `settings.general.item` 这个槽的 **children 授权**由 `ui-settings-general` 的 General section 条目声明(它在 `children` 里列了 `'settings.general.item': { kind: 'list', scope: 'root' }`),真正的 `renderSlot('settings.general.item')` 也发生在它的 `GeneralSection.tsx` 里。
- 但这个槽的**类型定义**(`SlotMap` 里的那一项)却放在 `locale` 包里——因为 locale 是「每个往这行注册东西的插件」都会依赖的公共底座。
- 外壳 `ui-settings-general` **既不声明这个槽的类型、也在类型层面不拥有它**,只负责在运行时 `register` + `renderSlot`。

这说明 Slot 系统里「类型归属、声明授权、实际渲染」是可以分属不同包的,目的是让依赖关系最小化、避免插件间互相 import。

## 拼装机制(回扣 Slot 系统)

把这页想成一棵 Slot 树:

```
ui-settings-general: 设置面板外壳
├── 导航区  ←── settings.section 账本(谁注册谁出现一个导航项)
│     ├─ 通用设置  (ui-settings-general 自带)
│     ├─ 模型      (ui-settings-models)
│     ├─ 内置插件  (ui-settings-plugins)
│     └─ Agent 预设 (ui-agent-preset)
└── 内容区(当前选中的 section)
      └── 「通用设置」section
            ├── 权限        ←─┐
            ├── 语言          │ settings.general.item 账本
            ├── 外观          │ (每行一个 feature 插件注册)
            ├── 字号大小      │
            ├── Coding Tools (外壳自带)
            ├── 工作步骤…    │
            └── 快捷键      ←─┘
```

- 外壳只提供「洞」(声明 slot)和两行自带内容;
- 每个功能插件在自己的 `apply` 里用 `ctx.slots.inject('settings.general.item', () => ctx.slots.register(...))` 把自己那一行塞进去;
- 插件没装 → 那一行就不存在;插件卸载 → 那一行自动消失(可撤销副作用)。

## 为什么要这么拆(设计意图)

1. **解耦**:主题归 `ui-theme`、权限归 `ui-permission-presets`、模型归 `ui-settings-models`,各管各的设置行,互不 import。
2. **按部署裁剪**:`whileServed` 让设置页随后端能力自动增减,没有的功能不会显示空壳设置。
3. **统一存储**:所有行都走 `ui-settings` 的 `configForms` 服务存到 Host 设置文档,不用各自实现传输和 schema。
4. **表现层可整体重写**:每一行的组件都是纯 props 消费品,改 UI 不碰业务。

## 一句话总结

**设置页 = `ui-settings`(定义能力和槽,不画界面)+ `ui-settings-general`(画外框和导航,自带两行)+ 一堆 feature 插件(每个往 `settings.section` / `settings.general.item` / `settings.plugins.tab` 注册自己的条目)。** 你在一张页面上看到的东西,背后是十几个插件协作的结果。
