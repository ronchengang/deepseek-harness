# 没有前端，只跑后端，能不能跑起来？

> 来源（代码坐实）：`packages/bundle/README.md`、`packages/bundle/headless/README.md`、`packages/bundle/base/`、`docs/architecture.md`（Profiles and bundles）、根 `README.md`。

## 直接答案：能，而且这是一等公民的运行方式

不带任何前端、只跑后端，完全能跑起来。这不是「阉割版」或「hack」，而是 dsh 架构明确支持、专门设计的运行模式。「一切皆插件」的全部意义就在于此：**UI 只是挂在 context 上的一组插件，把它们不挂，后端照常是一棵完整的 Cordis 插件树在跑。**

dsh 一共 5 个 shipped profile，其中 **4 个没有浏览器前端**：

| profile | 有前端吗 | 干什么 |
|---|---|---|
| `web` | **有**（browser GUI） | 交互式网页应用 |
| `headless` | **无** | 命令行跑一个任务，打印结果就退出 |
| `sdk` | **无** | 进程外 JSON-RPC 服务器，给别的程序调 |
| `sdk-minimal` | **无** | 最小 SDK 树（连 base 都不挂） |
| `acp` | **无** | 仅自动化的 Agent Client Protocol 服务器 |

## 最直白的例子：headless

`dsh-headless` 的 README 开头一句话就回答了你的问题：

> 「run one dsh task from the command line and print the final answer, then exits — **no GUI, no server, no browser**」

跑法：

```sh
dsh --profile headless "run the tests"
# 或从 stdin
echo "总结这些改动" | dsh --profile headless
```

它的特点：
- **没有 GUI、没有服务器、不开任何端口**，跑完就退出。
- 用的是**和其他所有界面完全一样的模型、工具、安全默认值**（同一个 `dsh-base`）。
- 适合脚本、CI、一次性任务。
- 还能 `--json` 输出事件流、`--session-id` 续接会话。

## 为什么能——架构上的原因

回扣前面几篇笔记的核心结论：

### 1. 前端和后端是两棵独立的 Cordis 树

`05`/`06` 讲过：Desktop 里「前端 = Web 客户端插件树」「后端 = Host 插件树」，两者通过 RPC/WebSocket 连接。既然是两棵独立的树，**只启动后端那棵、不启动前端那棵，完全成立**。

### 2. profile = 选择挂哪些 bundle

`02` 讲过 profile/bundle 机制。关键在 `packages/bundle/`：

- **`dsh-base`** 是共享的后端核心层：模型适配器、工具、持久化、沙箱和审批策略、设置、凭证、遥测。**这就是「后端」。**
- **`web-app`** 才是在 base 之上额外挂浏览器应用的那一层（mounts Web rows）。
- `headless` / `acp` / `sdk` 都是「`dsh-base` + 自己那一层非 GUI 应用」。

所以「只跑后端」= 挂 `dsh-base` + 一个非 GUI 的驱动层（headless runner / SDK server / ACP bridge），**就是不挂 `web-app`**。

### 3. 核心能力不依赖任何 UI

`core/*`（session、tools、agent、agent-loop、llm）这些后端骨架，没有一行代码依赖 `client/*`。依赖方向是单向的：UI 插件依赖后端服务，反过来不成立。这从 `packages/README.md` 的「扩展插件依赖 Service Definition，UI/hook/tool 插件用 `dsh-agent`」也能看出来——UI 是后端的消费者，不是它的前提。

## headless 跑起来做了什么（后端完整在工作）

从 README 的 run flow 能看到，没有前端时后端一样完整运转：

```
dsh launcher 启动 headless profile
  → 挂 dsh-base（完整后端）+ headless-runner + headless-startup
  → await 整个应用就绪（工具、适配器都挂好）
  → 解析任务（命令行参数或 stdin）、校验权限预设/审批策略
  → 解析 agentDefaultModel 选择
  → 解析/创建 Session 身份（默认 session-<uuid>，或 --session-id 续接）
  → 把任务作为 user message 提交给 Agent
  → Agent 跑 turn/step 循环：请求模型、调工具、写 session 日志（和有 GUI 时一模一样）
  → 把拥有的日志区间折叠成最终答案
  → 打印到 stdout，请求退出
```

注意：**session 日志、agent-loop、工具执行、模型请求这些核心流程（`03`/`09` 讲的）全都在跑**，只是没有人在浏览器里看着它、没有 WebSocket 把事件推给前端。final 答案直接打印到终端。

## 几个可直接验证的点

- **不开端口**：headless「opens no ports and leaves nothing running」。可以跑一个任务时 `netstat` 看，没有 3080 之类的监听。
- **凭证来源不同**：headless 默认**禁用**了 GUI 用的凭证存储（`credentials`/`authorization`/`deepseek-account` 几个 row 被 disable），改用环境变量 / `.env`。这正说明「无前端」profile 是通过 **patch 关掉若干 row** 实现的——又一次印证「挂/不挂插件」就是在塑形产品。想恢复存储凭证，往 `$DSH_HOME/profiles/headless/cordis.patch.yml` 加几行 `disabled: false` 即可。
- **会话互通**：headless 创建/续接的 Session 和 GUI 用的是同一套持久化。你可以用 headless 跑一个任务，再用 web 打开同一个 session 看（反之亦然），因为它们共享 `dsh-base` 的 session 持久化。

## 一句话总结

**能。后端是一棵完整自洽的 Cordis 插件树（`dsh-base`），前端只是另外一组挂在 context 上的 UI 插件。不挂 `web-app`、改挂 headless/sdk/acp 的驱动层，后端照常跑完整的 turn/step 循环、工具执行和 session 持久化——只是没有浏览器界面、不开端口、结果直接走命令行或 JSON-RPC。** 这恰恰是「一切皆插件」最想证明的事：换一层 bundle 就换一个产品形态，而核心不动。
